# Conformance kit

What a correct kernel must do, written as data, before any kernel exists. The kit judges a kernel; it is not one. This is stage 1 of [the bootstrap](../ARCHITECTURE.md#8-building-dodona-with-dodona).

It covers what the formal models cover and no more: obligation status, intent status with exceptions and separation, what the planner reruns, the shown level and non-vacuity, parents and children, repeated attempts, platforms, and decisions flagged on change. [`spec/CLAIMS.md`](../spec/CLAIMS.md) lists what is not modelled, and therefore not in the kit.

Every scenario names the claim it bears on and the model cases it covers. Each planted defect in the formal models has at least one scenario that a kernel repeating that defect fails. The repository checks enforce this.

## How a kernel is judged

`tools/run_kit.py -- <kernel command>` starts the kernel once per scenario, with the scenario as JSON on standard input. The kernel is shown what happens in each step and nothing else: the expected results and the notes about the scenario are removed first. The kernel prints `{"results": [...]}` with one result per step. Every step shown in the tables below is valid at any point of a scenario, in any order and any number of times; where a step has nothing to act on, the section says what happens. In every kind, a step that names something the scenario does not have (a criterion, an obligation, a definition, a run, a child, a ticket, a platform, a key, an intent) changes nothing, and a step whose value is not one the tables allow (a gate, a verdict or a level that does not exist) changes nothing either, with one exception: a gate in a tree scenario that is text other than `hard` or `soft` counts as `hard` (see Tree scenarios). A step that carries a value of another type than the tables give (a name that is not a string, a verdict that is a number, a list where a word belongs) changes nothing either, in every kind, as if the value were one the tables do not allow. A kernel answers every step; it never stops on one.

A kernel reads every input as strictly as the [canonical encoding](../protocol/canonical-encoding.md) writes: a key repeated in one object, or a number that is not written as an integer (`1.0`, `1e0`, `10E-1`), makes the whole input refused, and the kernel exits with a status other than 0 (except the `status` command, which answers every input with one JSON object and exits 0, a refusal included: see "How a project's status is judged"). Otherwise a record could be signed with one value and read with another. `tools/run_input_cases.py` judges this: a control without a fault must exit 0, and each faulty input must end with any status other than 0 that the kernel returned on its own. A kernel that could not be started, ran out of time, or was ended by the operating system (a negative status for a POSIX signal, or a status from 0xC0000000 to 0xCFFFFFFF, the NTSTATUS error range in which Windows reports a process ended by an exception) answered nothing, and that case is `UNFINISHED`, not a refusal. Other endings from outside that leave an ordinary status, such as a Windows kill or a crash the kernel reports itself, cannot be told apart and still count as refusals. The judge ends with the same report as the scenario judge, counted under `cases`, and exits 0, 1 or 2 as the scenario judge does; a run with an unfinished case is unfinished even after a mismatch. A scenario matches when every field its steps expect is present and equal. The scenario judge reports a completed but wrong answer as `MISMATCH` and a process that could not complete as `UNFINISHED`. It exits 0 for a complete match, 1 for a completed suite with mismatches, and 2 for an unfinished or empty suite. Both planted-defect runners count a rejection from the scenario, ledger, core-key, attest, harness, strict-input, provider session, host-check or status judge only when two complete reports reject the same named case. The JavaScript runner also uses this rule for its canonical and path judges. The host-check and status reports keep skipped cases outside their judged totals.

`tools/run_vectors.py -- <kernel command>` judges the canonical-encoding vectors. The command must exit 0 with a JSON object naming the exact canonical text and SHA-256 digest, or the exact refusal reason. A completed usable answer that differs is a named mismatch. A launch failure, timeout, nonzero exit, explicit disk-full diagnostic, or output without a usable acceptance or refusal leaves the vector unfinished. The footer counts `vectors`, `matched` and `unfinished`, lists mismatch names in `rejected`, and reports `all_matched`. The judge exits 0 for a complete match, 1 for completed mismatches, and 2 if a vector or the judge was unfinished or no vector ran.

The path-vector judge uses the same footer and exit meanings for its single-path and collision commands. It gives text accepts, text refusals, byte refusals and named collision cases distinct identifiers. A path answer requires a boolean acceptance or a string refusal, and a collision answer requires a list of two-string pairs. A completed answer that differs from the exact expectation is a named mismatch. A failed process, disk-full diagnostic or unusable answer leaves the vector unfinished. Pair order does not matter, but extra pairs, duplicates and unrelated paths are mismatches.

### Evidence scenarios

A scenario gives the obligations with what each depends on, the starting content of every definition, the starting tool, and whether the backend is up. Content and tools are opaque strings standing for identities.

| Step | Meaning |
|---|---|
| `{"edit": {"definition": D, "to": H}}` | The content of definition D becomes H |
| `{"repin": {"to": T}}` | The pinned tool becomes T |
| `{"backend": {"to": "up" or "down"}}` | The execution backend becomes reachable or unreachable |
| `{"submit": {"obligation": O, "as": J}}` | A check of O is asked for. With the backend up, run J starts on the inputs as they are now. With it down, the outcome is `unavailable` and no run exists |
| `{"complete": {"run": J, "verdict": "passed" or "failed"}}` | Run J finishes with that verdict for the inputs it was given |
| `{"lose": {"run": J}}` | Run J ends with no result |

The result after each step is an object with one entry per obligation: `{"status": S}` and, when the status is `unknown`, `"reason": R`.

- `status` is `passed`, `failed`, `conflict` or `unknown`, by the rule in [the data model](../MODEL.md#4-status). Only results recorded for the current inputs count: the content of everything the obligation depends on, and the tool.
- `reason` is `pending` if a run on the current inputs is in flight; otherwise the outcome of the most recent attempt on the current inputs that left no result, `unavailable` or `error`, where attempts are ordered by when they were asked for (their `submit`), not by when they ended; otherwise `never-run`. A lost run gives `error`.
- Recorded results take precedence over a run in flight: an obligation that has passed stays `passed` while it is being checked again.
- A run is in flight from the `submit` that started it until it is completed or lost. A `complete` or `lose` naming a run that is not in flight changes nothing. A `submit` under a name that is in flight changes nothing, whatever the backend and whichever obligation it asks for: names are shared by all obligations, and no `unavailable` is recorded. Once a run has ended, by a `complete` or a `lose`, its name may be used again.

### Intent scenarios

A scenario gives the criteria with their gates as first written, and a policy: `exception_separation`, the least separation at which an exception takes effect, and `min_hard_gates`.

| Step | Meaning |
|---|---|
| `{"confirm": {}}` | The owner confirms the gates as they stand |
| `{"check": {"criterion": C, "status": S}}` | The check behind C now has status S: `unknown`, `passed`, `failed` or `conflict` |
| `{"edit": {"criterion": C, "to": G}}` | The gate of C is changed directly, not by an exception |
| `{"amend": {"criterion": C, "to": G, "by": "owner" or "worker", "claims": L, "source": "declared" or "attested"}}` | An exception is asked for. `claims` is the separation level the record claims and may be absent. `source` says who stands behind the claim and is `declared` when absent |

The result after each step has `"status"`, and after an `amend` step also `"amendment": {"takes_effect": true or false, "level": L}`. Every `amend` step gets that answer. One that names a criterion that does not exist, or whose `to`, `by`, `claims` or `source` is not a value the table allows, does not take effect, changes nothing, and has the level `self`.

- `level` is the separation the kernel grants. It is `self` if the worker is the grantor or nothing is claimed. Otherwise it is the claimed level, capped by its source: a `declared` claim earns `helper` at most, an `attested` one `cross-make` at most.
- An exception takes effect only if the owner granted it and its level is at or above the policy floor. The levels in order are `self`, `helper`, `apart`, `tested`, `cross-make`, `credentialed`. An exception that takes effect is the owner's own act and leaves the intent confirmed.
- A soft gate never affects the status, whatever its check says.
- `min_hard_gates` is at least 1. A lower value is treated as 1.
- An `edit` that sets a gate to what it already is changes nothing.
- An `amend` that names a criterion the intent does not have changes nothing: the amendment does not take effect and its level is `self`, whoever asks and whatever it claims.
- `status` is the first of these that applies: `draft` if the owner has not confirmed, or a gate was edited since; `unguarded` if there are fewer hard gates than `min_hard_gates`; `open` if any hard gate's check is not `passed`; `delivered` if any deferred gate's check is not `passed`; otherwise `fulfilled`. An intent with no deferred gate is therefore fulfilled as soon as it is delivered.

`uncovered` and `overdue` are left out: every criterion has a check, and there is no clock.

### Plan scenarios

A scenario gives `definitions`, each with what it `depends_on` and the `file` it is in; a `granularity`, `definition` or `file`; `obligations`; and the starting content of each definition and each tool. An obligation either has `targets` (definitions) and perhaps a `tool`, or is `artifact_of` another obligation, meaning it works on what that obligation produces, with a `tool` of its own.

| Step | Meaning |
|---|---|
| `{"edit": {"definition": D, "to": H}}` | The content of D becomes H |
| `{"repin": {"tool": T, "to": H}}` | Tool T becomes H |
| `{"run": {"obligation": O}}` | O is run, if it is planned and, where it works on another obligation's product, that other obligation has a result for the current inputs. Otherwise nothing happens |

The result after each step has `"plan"`: the names of the obligations with no result for their current inputs, sorted. After a `run` step it also has `"ran"`, true or false.

- An obligation's inputs are the content of its targets and of everything they depend on, however indirectly, and its tool if it has one. An obligation that is `artifact_of` another has that other's inputs as well as its own tool.
- With granularity `file`, the content of a definition counts as the content of every definition in the same file. Only the targets and what they depend on are followed; what a file-mate depends on is not.
- An obligation may be `artifact_of` one that is itself `artifact_of` another.
- A result is kept for the inputs it was run on, and counts again whenever the inputs are the same again.

### Assurance scenarios

Each step is `{"judge": {"links": {...}, "defects": {...}}}`. The scale, weakest first, is `none`, `asserted`, `observed`, `sampled`, `bounded`, `proven`. `links` gives a level for some or all of `spec-to-code`, `code-to-runs` and `runs-to-world`; a link that is absent or null was not reported. `defects` gives the status of each planted defect of a check: `passed`, `failed` or `unknown`.

The result has `"shown"`: the weakest of the three links, on the scale `none`, `asserted`, `observed`, `sampled`, `bounded`, `proven`, where a link not reported counts as `none`. It also has `"non_vacuous"`: `none-planted` if there are no defects, `shown` if every one is `passed`, otherwise `not-shown`.

### Tree scenarios

A scenario gives a `root` and `children`, each with the gate of its one criterion, `hard` or `soft`, and a policy with `min_hard_gates`. There may be no children. Tree scenarios know only those two gates. Any gate that is a string other than exactly `hard` or `soft` (`Hard`, `Soft`, `deferred`, any other text), whether at the start, in an `edit` or in an `add`, counts as `hard` ([decision 0030](../decisions/0030-the-hard-gate-floor-is-counted-over-the-tree.md)): a mistake in writing a gate can only make delivery harder, as with a gate nobody can read in status scenarios. `deferred`, a gate status scenarios do know, is not one here, so it too counts as `hard`. A starting gate that is not a string makes the scenario invalid. A gate that is not a string is a value of the wrong type, and the step changes nothing. Adding a child that is already there, setting a gate to what it already counts as, or a step that names a child that is not there, changes nothing.

| Step | Meaning |
|---|---|
| `{"confirm": {}}` | The owner confirms the tree as it stands |
| `{"check": {"node": N, "status": S}}` | The check behind N's criterion now has status S, one of `unknown`, `passed`, `failed` or `conflict`. N is `root` or a child |
| `{"edit": {"node": N, "to": G}}` | N's gate is changed directly |
| `{"remove": {"child": K}}` | Child K is removed |
| `{"add": {"child": K, "gate": G}}` | Child K is added, its check unknown |

The result has `"status"`, the first of these that applies: `draft` if the owner has not confirmed, or anything was edited, added or removed since; `unguarded` if the tree counts fewer hard gates than `min_hard_gates`, or fewer than one, counting the root and every child; or if any child has no hard gate (decision 0030). A child is not held to the policy's number on its own: moving a criterion into a child loses nothing (decision 0017). `open` if any hard gate's check is not `passed`; otherwise `delivered`.

### Attempts scenarios

| Step | Meaning |
|---|---|
| `{"take": {"as": T}}` | A ticket T is taken for an attempt at judging the current target. The attempt is open |
| `{"close": {"ticket": T, "result": "agreed" or "refused"}}` | The attempt is closed with that result |
| `{"change_target": {}}` | The thing being judged changes |

A scenario may give `claims`, the separation level the act claims, and `refusals_before_cap`, a whole number of at least one, 2 when absent. Any other value of `refusals_before_cap` (zero, a negative number, a fraction, a string) makes the scenario invalid, and the kernel refuses it as it refuses any invalid input: a non-zero exit and no result. Closing a ticket that was never taken, or is already closed, changes nothing. A ticket taken before a change of target can still be closed.

The result has these fields. Every field is worked out from the attempts as they stand now, in the order they were taken; the first two from those on the current target only. So closing an earlier open attempt as agreed can clear `retried`.

- `"result"`: `none` if there are none; `agreed` if every one is closed as agreed; otherwise `refused`. An open attempt counts as a failure.
- `"shopped"`: true if some attempt closed as agreed was taken after one that is not agreed.
- `"cap"`: `helper` when shopped, or when retried and the line has at least `refusals_before_cap` attempts that are not agreed, otherwise null (decision 0031). A change of target does not reset the count, and an agreement after a change keeps its grade only until that limit: the kernel cannot tell a real fix from a trivial change.
- `"attempts"`: how many tickets have been taken in all, across changes of target.
- `"retried"`: true if, among all attempts across changes of target, some attempt closed as agreed was taken after one that is not agreed.
- `"granted"`, when the scenario gives `claims`: the claimed level, lowered to `helper` if `cap` is `helper` and the claim was higher. The cap never raises a level.

### Platforms scenarios

A scenario gives `keys` (sets of inputs), any number of `platforms`, whether policy allows a record from one platform to stand in for another, `stand_in_allowed`, and whether the provider claims its results do not depend on the platform, `provider_claims`, true when absent. Each step is `{"record": {"key": K, "platform": P, "verdict": "passed" or "failed"}}`. A second record for the same key and platform with the same verdict changes nothing; with the other verdict it makes that platform's own status `conflict`.

- `"status"`, by key then platform: the platform's own verdict if it has one, or `conflict`; otherwise another platform's verdict for the same key, if standing in is allowed, the provider claims platform independence, and the claim is verified; otherwise `unknown`. The claim is verified for a key when that key has the same verdict on at least two platforms, whether passed or failed, and no platform, the one asked about included, has recorded the other verdict for that key. Another key agreeing verifies nothing about this one. When a stand-in is allowed all of the key's verdicts are the same, so it does not matter which platform's is taken.
- `"stood_in"`: the list of `[key, platform]` pairs whose status rests on another platform's record, sorted by key and then platform.
- `"reproducibility"`, by key: `differs` if the key has both verdicts recorded, on one platform or several; `agrees` if at least two platforms have a verdict and all are the same; otherwise `unknown`.

### Decisions scenarios

A scenario gives `names` with their starting content and the list of names a decision `governs`. The decision records the content each governed name had at the start.

| Step | Meaning |
|---|---|
| `{"edit": {"name": N, "to": H}}` | The content behind N becomes H. A null H means N no longer exists |
| `{"review": {}}` | The decision is reviewed against what its names are now, and records that. If any governed name no longer exists, nothing happens |

The result has `"flagged"`: true exactly when the content behind some governed name is not the content the decision recorded for it. Only a review changes what is recorded.

### Acts scenarios

How separate was the party behind an act of judgement ([decision 0024](../decisions/0024-separation-is-graded-not-enforced.md)). A scenario gives a `policy` with `attestors`, a map from key name to a key in hexadecimal, and `makes`, a list of groups of `vendor/family` names that count as the same make. A group that is not a list of strings is ignored, and a name matches only a name equal to it, never part of one. Each step is `{"grade": R}` where R is an act record ([schema](../protocol/act-record.schema.json)). The keys in the kit are fixtures, public by design.

The result has `"claims"`, the level the record's facts would support if they were all true; `"level"`, the level granted; and `"source"`, `attested` if the granted level is above `helper` and otherwise `declared`.

The facts:

| Fact | Holds when | Reads |
|---|---|---|
| distinct | `actor.id` is not `worker.id`, and `actor.session` is not `worker.session` | `actor`, `worker` |
| started | `actor.started_by` is present and is not `worker.id` | `actor`, `worker` |
| briefed | `brief.issued_by` is `kernel` or `owner` | `brief` |
| given | `given` is present and not empty, and every item's role is `work`, `criteria`, `brief`, `known-wrong` or `known-right` | `given` |
| fresh | `fresh_context` is true | `fresh_context` |
| kept | `transcript` is present | `transcript` |
| tested | `known_bad.supplied_by` is `kernel` or `owner`; `rejected_wrong` and `accepted_right` are both true; and `given` holds an item with role `known-wrong` and content `known_bad.wrong`, and one with role `known-right` and content `known_bad.right` | `known_bad`, `given` |
| other make | `actor.make` and `worker.make` both give `vendor` and `family`, both `vendor/family` names appear in `makes`, and they are in different groups | `actor`, `worker` |

`claims` is `self` if distinct does not hold; otherwise `helper`; `apart` if started, briefed, given, fresh and kept also hold; `tested` if tested holds as well; `cross-make` if other make holds as well. Each level needs every fact of the levels below it.

A fact is **vouched for** when every field it reads is listed in `attestation.covers`, `attestation.key` names a key in `attestors`, and `attestation.mac` is the HMAC-SHA256, under that key, of the canonical encoding of `{"covers": C, "fields": F}`, where C is `covers` and F holds each covered field of the record under its name. A record with no attestation, a key the policy does not name, or a mac that does not match, has no fact vouched for. A covered field that the record does not have is left out of F. The fact distinct needs vouching like any other: without it nothing above `helper` is granted.

The check value is exact:

- `mac` is 64 lowercase hexadecimal digits and is compared in full. The same value in uppercase, or one that matches only in part, vouches for nothing.
- `covers` is used in the order the record gives it. It must already be sorted as the canonical encoding sorts keys, with no name repeated. A list in any other order, or with a repeat, vouches for nothing, even if the mac was made over that very list.
- A key in `attestors` is a non-empty string of lowercase hexadecimal digits, of even length. Anything else (an empty string, an odd number of digits, an uppercase digit, a character that is not a digit) names no key: nothing is vouched for under it. The attestation's `harness` must be the same as its `key`: a value that names one harness and was made with another's key vouches for nothing. An attestation with no `harness` vouches for nothing either.

**A check value binds the whole record.** No level above `helper` is granted unless `covers` lists every field the record has at the top level, other than `attestation` itself, and lists at least `ticket`, `kind`, `target`, `result` and `lineage`. So nothing can be added to a signed record, or changed in it, without breaking the mac: not what was judged, not the ticket, and not a field nobody reads today. An attestation with a field other than `harness`, `key`, `covers` and `mac` vouches for nothing. A record that does not meet this keeps its `claims` and is graded `helper`, `declared`.

**A malformed record is `self`.** Its `claims` is `self`, its `level` is `self` and its `source` is `declared`, whatever it says and whoever signed it. A record is malformed when any of these is true, and in no other case:

- It has a field at the top level that the act record does not define: anything other than `ticket`, `kind`, `target`, `result`, `lineage`, `actor`, `worker`, `brief`, `given`, `fresh_context`, `known_bad`, `attempt`, `transcript` and `attestation`. A field nobody signs cannot ride along on a signed record.

- `actor` or `worker` is missing or is not an object, or the `id` or the `session` of either is not a string. A missing `id` or `session` is not a string.
- A field that is present has the wrong type:
  - `brief` is not an object;
  - `given` is not a list of objects, each with a string `role` and a string `content`;
  - `fresh_context` is not a boolean;
  - `transcript` is not a string;
  - `known_bad` is not an object, or lacks a string `wrong`, `right` or `supplied_by`, or a boolean `rejected_wrong` or `accepted_right`;
  - `attestation` is not an object with a string `key`, a string `mac` and a list of strings `covers`;
  - `kind`, `target` or `result` is not a string;
  - `lineage` is not an object;
  - `ticket` is not a string;
  - `actor.started_by` is present and is not a string;
  - `attempt` is not an object with an integer `number` and an integer `prior`.

A field that is simply absent does not make a record malformed, except that `actor` and `worker` must be there. A value of the right type that no table allows, such as a role of `other`, is not malformed either.

`level` is the highest level, not above `claims`, that is `self` or `helper`, or all of whose facts and the facts of the levels below it are vouched for by a check value that also binds what was judged. `credentialed` is never granted.

### Status scenarios

What a kernel reports about a whole project. A scenario gives:

- `self`: this kernel's `writer` name and its `platform`.
- `policy`: `min_hard_gates`; `required`, the intents that must be delivered; `trusted_writers`; `floors`, the least separation at which an act of each kind counts; and `attestors` and `makes` as in acts scenarios.
- `obligations`: for each name, the `preimage` of its core key as things stand ([vectors](vectors/core-key.json)).
- `intents`: for each id, its `owner`, its `worker`, its `children`, optionally `words`, the intent as written, and its `criteria`, each with a `gate`, `checked_by`, a list of obligation names, and optionally `words`, the criterion as written.

| Step | Meaning |
|---|---|
| `{"append": {"kind": "evidence", "body": B}}` | A record is added to the ledger. B has `obligation`, `preimage`, `core_key`, `platform`, `verdict` and `writer` |
| `{"append": {"kind": "act", "body": R}}` | An act record is added to the ledger |
| `{"change": {"obligation": O, "preimage": P}}` | The inputs of O are now P |
| `{"set_gate": {"intent": I, "criterion": C, "to": G}}` | A gate is edited directly |

The result has `obligations` and `intents`, each an object with one entry per name; `project`, an object with a `status`; and `rejected`, a number. A floor that policy does not give is `self`.

**Obligations.** An evidence record is *not a record* if its body is not an object, if its `verdict` is not `passed` or `failed`, or if it lacks `obligation`, `platform`, `writer`, `core_key` or `preimage`. A field of the wrong type counts as lacking: `obligation`, `platform`, `writer` and `core_key` must be strings and `preimage` an object. Such an entry does not count for anything and is not counted as rejected either. Any other evidence record is *rejected* if its `core_key` is not the identity of its own `preimage`, or its preimage is one the core-key rules say must be refused; `rejected` is how many such records the ledger holds. A record that is not rejected *counts* for the obligation it names, and for no other, when its writer is this kernel or one of `trusted_writers`, its platform is this kernel's, and its `core_key` is the identity of the obligation's preimage as things stand. An obligation is `passed` if records count and all are passed, `failed` if all are failed, `conflict` if they differ, and otherwise `unknown` with `"reason": "never-run"`. An obligation named in a `checked_by` that the scenario does not define is `unknown`, `never-run`: the criterion has an obligation, and it has not passed.

**A gate nobody can read is hard.** A criterion whose `gate` is not exactly `hard`, `soft` or `deferred` (`Hard`, a gate with a hidden character, anything else) counts as `hard` in every rule: in the floor, in `open`, in `gates`. A mistake in writing a gate can only make delivery harder, never easier. The baseline keeps the gate as written.

**Baseline.** Lists marked sorted are sorted as the canonical encoding sorts keys. The baseline of an intent is the identity of `{"owner": O, "words": T, "children": [sorted], "criteria": {C: {"words": W, "gate": G, "checked_by": [sorted]}}}`, where T is the intent as written, all of it, and W is each criterion's wording, each the empty string when the scenario gives none. Changing anything in what the owner confirmed, a title, a row, a hidden comment, changes the baseline. Rewording a criterion changes the baseline, so a confirmation of the old words stops counting.

**Acts.** An act record is graded as in acts scenarios, a malformed one as `self`, with one more rule: if its `worker.id` is not the intent's `worker`, its level is `self`. An act entry whose body is not an object takes part in no rule. An intent is *confirmed* when the ledger holds an act of kind `confirm-baseline` whose `lineage.intent` is the intent, whose `result` is `agreed`, whose `target` is the intent's baseline as things stand, whose `actor.id` is the intent's owner, and whose level is at or above `floors["confirm-baseline"]`.

**Intent status** is the first of these that applies: `draft` if not confirmed; `uncovered` if a criterion has no obligation; `unguarded` if there are fewer hard gates than `min_hard_gates`; `open` if some hard criterion has an obligation that is not `passed`; `delivered` if some deferred criterion has one that is not `passed`; otherwise `fulfilled`.

Each intent also reports:

- `baseline`: the baseline of the intent as things stand, the identity defined above. It is what a confirmation must name.
- `gates`: how many criteria are `hard`, `soft` and `deferred`, and `deferred_open`, how many deferred criteria are not met.
- `score`: `met`, how many criteria are met, `of` how many criteria. A criterion is met when it has at least one obligation and every one is `passed`. A criterion that nothing checks is never met.
- `shown`: `level` and `criterion`. An evidence record may state a `level`, one of the scale in the assurance scenarios; one that states no level, or something not on the scale, is `asserted`. A record that states the level `none` is taken at `none`: it is on the scale. An obligation that is `passed` has the strongest level among the records that count for it; any other obligation has `none`. A criterion has the weakest level among its obligations, and `none` if it has no obligation. `level` is the weakest among all the intent's criteria, soft ones included, and `criterion` is the first criterion at that level, in the order in which the canonical encoding sorts keys. An intent with no criteria shows `"level": "none"` and `"criterion": null`.
- `exceptions`: `counted` and `below_floor`. Among the agreed act records of kind `grant-amendment` whose `lineage.intent` is the intent: one counts if its `actor.id` is the intent's owner and its level is at or above `floors["grant-amendment"]`; every other is below the floor. A refused one is neither. In status scenarios an exception changes no gate; the intent scenarios judge what it changes.
- `separation`: there must be one act of kind `confirm-baseline` and one of kind `match-check` for each pairing of a criterion with an obligation that checks it. For each, take the highest level among the agreed act records for it in the ledger: for the confirmation, those that would confirm the intent but for the floor; for a pairing, those of kind `match-check` whose target is the identity of `{"intent": I, "criterion": C, "obligation": O}`. A match-check is found by its target alone. Its `lineage` is not read: one whose lineage names another criterion, or another intent, still counts for the pairing its target names, and for no other. With no such record the level is `self`. `weakest` is the lowest of these levels; `act` is the kind it belongs to, `confirm-baseline` if both kinds have it; `apart_or_better` counts those at `apart` or above; `of` is how many there must be.

**Project status** is `nothing-required` if `required` is empty; otherwise `failed` if a hard criterion of a required intent has an obligation that is `failed` or `conflict`; otherwise `passed` if every required intent is `delivered` or `fulfilled`; otherwise `unknown`. A required intent that the scenario does not define counts as not delivered, so the project cannot be `passed`.

A ledger may hold entries of other kinds, and an evidence body may carry more fields than those named. A kernel ignores both: they take part in no rule.

A step that names an obligation, intent or criterion that does not exist changes nothing. A kernel answers every step and never stops on one: not on a body that is empty or is not an object, not on an act with no actor, not on a name nothing defines. The floor for `match-check` is read by no rule yet: a pairing's level is reported, and nothing is withheld for it.

What an exception changes, children and deferred time limits are left out of status scenarios; the intent and tree scenarios cover them.

## The ledger, and core keys

Two more things are judged, each by its own tool.

**Core keys.** `tools/run_key_vectors.py -- <kernel command>` starts the kernel with a preimage on standard input and requires `{"core_key": "<identity>"}`, or `{"refused": "<reason>"}` for the vectors that must be refused ([vectors](vectors/core-key.json), [more vectors](vectors/core-key-more.json)). Both answers come with exit 0. A completed answer that differs, including output that is not JSON, is reported as `MISMATCH` under the vector's name. A key command that could not be started, timed out, was ended by a signal or exited with a status other than 0, and a judge that could not read its vectors, end the run as `UNFINISHED`, whatever was compared before. The last line is `{"vectors", "matched", "all_matched", "unfinished", "rejected"}`, `rejected` naming each vector that did not match. The judge exits 0 for a complete match, 1 for a completed run with mismatches, and 2 for a run that did not complete or in which no vector ran.

- Every set in a preimage (`specified_by`, `targets`, `closure`, `declared`, `mapping`) must arrive sorted as the canonical encoding sorts keys, that is by UTF-16 code units, with no member repeated. Every set is checked, not only `closure`. Two members in descending order are unsorted. A repeat in any set is refused. The reason is `unsorted-set` in each case.
- A field the preimage definition does not have is refused. For `platform`, at the top level or inside `inputs`, and whatever its value, null included, the reason is `platform-in-core-key`. Any other field at the top level that the definition does not have is refused with the reason `unknown-field`.

**The ledger file** ([format](../protocol/ledger.md)). `tools/run_ledger_cases.py -- <kernel command>` gives the kernel two subcommands. `ledger-append` takes `{"ledger": "<file>", "kind": K, "body": B, "wait_ms": N}` and answers `{"appended": "<identity>"}` or `{"refused": "locked", "corrupt" or "bad-request"}`. `ledger-read` takes `{"ledger": "<file>"}` and answers `{"entries": [...], "torn": true or false}` or `{"refused": "corrupt", "at": N}`. The judge appends entries through the kernel and requires the file to be, byte for byte, what the reference encoder produces; damages the file in each of the ways listed in `conformance/ledger/cases.json`, including a torn ending at every byte; reads each whole file in `conformance/ledger/more-damage.json`; has two kernels append at once and requires every entry to survive; and holds the lock itself and requires `locked`. A kernel that answers wrongly, including output that is not JSON from a kernel that exited with 0, is reported as `MISMATCH` under the check's name. A kernel that could not be started, timed out, was ended by a signal or exited with a status other than 0, a writer that could not be started or did not finish, and a judge that could not go on (a file it could not write, a temporary folder it could not remove), end the run as `UNFINISHED`, whatever was compared before. The last line is `{"checks", "matched", "all_matched", "unfinished", "rejected"}`, `rejected` naming each check that did not match. The judge exits 0 for a complete match, 1 for a completed run with mismatches, and 2 for a run that did not complete or in which no check ran.

- `kind` is any non-empty string. A reader keeps entries of every kind, and an append after an entry of a kind it gives no meaning works as after any other.
- A line is exactly `dodona1`, one space, the length in decimal with no sign and no leading zero, one space, 64 lowercase hexadecimal digits, one space, the payload, and a line feed. Anything else is corrupt at that line: two spaces, a tab, a byte-order mark, an empty line, bytes after the payload, an uppercase digit, another first word.
- The length and the checksum are both compared with the payload. `previous` must be exactly the identity of the entry before, and null in the first entry only. A payload that is not an object with exactly `previous`, `kind` and `body`, or that nests deeper than 64 levels (the entry itself is the first), is corrupt.
- An append to a corrupt ledger answers `{"refused": "corrupt"}` and leaves the file as it was, unless the request itself is bad (below).
- A `ledger-append` with no string `kind`, with no `body`, or whose entry would nest deeper than 64 levels, answers `{"refused": "bad-request"}` and writes nothing: no entry, no file, no lock left behind. An entry of exactly 64 levels is appended, and an append after it works. The request is judged before the lock is taken and the ledger read, so a bad request to a locked or corrupt ledger is still `bad-request`, and so is a request nested too deep to be read at all.

## How a host is judged

`tools/run_provider_cases.py -- <host command>` starts the host once per case and has it run the misbehaving provider in that mode. A case matches when the host reports the expected outcome and reason, returns within the deadline plus a grace period, and nothing the provider started is still running. The first case is a well-behaved provider that must be accepted: a host that refuses everything would otherwise pass.

The command below asks for one JSON object on standard output and says nothing of the exit status. The reference host and both kernels exit 0 after printing a session's answer, their refusals (`closed`, `deadline`, `malformed` and the rest) included, and exit otherwise only when they could not complete it. The judge therefore counts only an answer completed with exit 0: this is how the judge reads a run, not a new rule of the session. A host that could not be started, ran out of time (the judge ends it through the handle it holds on it) or exited other than 0 has answered nothing, whatever it printed, and the case is unfinished, not a mismatch. So is a case whose fixture could not be observed: a transcript or process-id file the judge could not read, no process id recorded, a missing transcript (every mode records hello first, and no case declares one absent), a recorded process present after the host returned that never acknowledged, a survivor not seen to stop, or a temporary folder that could not be removed; an unfinished case's folder is kept as evidence. A completed answer that is wrong or too late, a wrong transcript, and a provider process that acknowledged it was still running before cleanup began are mismatches, named in `rejected`. Survival is told by the fixture, not by a process id or command line, since an id read from a file may by then be another process's: each run makes a random nonce, the judge creates the case's probe file (`DODONA_TEST_PROBE`), and every waiting fixture process creates `alive-<pid>` holding the nonce in `DODONA_TEST_ACK`; then, in a `finally` even when observation failed, the judge creates the stop file (`DODONA_TEST_STOP`), on which each creates `stopped-<pid>` and exits. Marker files are created only if absent. A process that acknowledges only the stop file survived but was not seen before cleanup, and is unfinished. Otherwise a recorded id, once checked to be plain decimal digits in the platform's range, is only asked whether it exists (signal 0, then `ps -o stat= -p <id>` on POSIX so that a zombie counts as exited; `OpenProcess` and a zero wait on Windows). That cannot tell whose the process is, so a present id that never acknowledges is unknown and never a pass. Exit 0 without one readable JSON object naming an `outcome` is no answer, and the case is unfinished. The fixture's files are read only if they are regular files of a size the fixture writes; anything else is quarantined. The judge signals no process; only a host that outruns the outer timeout is ended, through the handle on the process the judge started itself. Every look and wait after the host returned shares one deadline on the monotonic clock. A fixture process that does not poll (one blocked reading a pipe a host left open) cannot acknowledge: this is a limit of observing by cooperation, and such a case ends unfinished. It ends with the same footer as the other judges, counting `cases`, and exits 0 when every case matched, 1 when the run completed with mismatches and 2 when anything did not finish.

### Session

`tools/provider_host.py` is the reference ([decision 0033](../decisions/0033-a-kernel-hosts-providers.md): a kernel's `session` command is judged the same way).

**The command.** `<host> --deadline-ms N --max-line N --max-log N -- <provider command and arguments>`. The host starts the provider, holds one session with it and prints one JSON object: `{"outcome": "ok"}` or `{"outcome": "error", "reason": R}`, with `"log_bytes"`, how many bytes the provider wrote to standard error, and `"log_truncated"`, true when that was more than `--max-log` and only that much was kept.

**The session.** The host sends `{"type": "hello", "protocol": ["0.2"], "limits": {"max_line_bytes": L, "deadline_ms": D}, "echo": E}`, where L and D are the limits it was given and E is a string with non-ASCII letters and control characters. The provider must answer `{"type": "manifest", "echo": E, "manifest": {...}}` with E unchanged: `bad-manifest` otherwise, or when `manifest` is not an object. The host then sends one request, `{"type": "request", "id": "1", "deadline_ms": D, "capability": "decision.index", "body": {"files": []}}`, and requires an answer with id `1` (`wrong-id`) that is a `result` (`provider-error` for an `error`, `unexpected` for anything else) for `decision.index` (`wrong-capability`). It sends `shutdown`; anything more from the provider after its answer is `unexpected`.

**Reading.** Every line the host reads is one message ended by a single line feed: a carriage return before it or a byte-order mark is `framing`; a line longer than `--max-line` is `too-long`, and is never held whole; bytes that are not UTF-8 are `encoding`; text that is not one JSON object with a string `type` is `malformed`, and `NaN` or `Infinity` is not JSON; the provider closing its output is `closed`. Standard error is read all the time and kept only up to `--max-log`. In a session JSON is read as JSON: the strict reading of a check does not apply, so a fraction, a repeated key or deep nesting in a valid message is not `malformed`. One deadline, on a clock that cannot be set back, covers the whole session, sending as well as waiting: `deadline` when it passes. After `shutdown` the host gives the provider up to one second (less if the deadline is nearer) to exit; anything it sends in that time is `unexpected`, and a provider still running then is ended with its process group, its answer standing. However the session ends, every process in the provider's process group (on Unix) or job (on Windows) is gone when the host returns; a process that deliberately leaves both is beyond what a host can promise to end.

### Host checks: rules a schema cannot express

`tools/run_check_cases.py -- <host command>` judges any host that takes one check from a provider to a verdict. The reference is `python tools/host.py check` ([decision 0026](../decisions/0026-the-first-host-and-status-are-stage-0-helpers.md)); a kernel that hosts providers is judged the same way ([decision 0033](../decisions/0033-a-kernel-hosts-providers.md)). `provider/misbehaving_checker.py` sends only well-formed messages and breaks one rule in each mode; `provider/check-cases.json` lists what the host must do. The judge stands in for the executor with `provider/fake_executor.py`, and judges from what the provider and the executor record: the runs started, the keys they were started under, what the start request carried, the reports passed back, the echo of `hello` and the closing `shutdown`. The host is not meant to write those records, but nothing stops a host built to forge them: the judge shows that a host which skips a step or changes what it passes on is caught, not that a host written to deceive the judge is.

**The command.** The host is started once per case with one JSON object on standard input and prints one JSON object on standard output:

- In: `{"root": DIR, "provider": [argv], "obligation": O, "inputs": [{"path", "identity"}], "tools": [{"name", "version", "digest"}], "platform": P, "executor": [argv], "deadline_ms": N}`. `root` is the directory the provider is started in and paths are relative to. `deadline_ms` bounds each message the host sends or waits for.
- Out: `{"outcome": "verdict", "verdict": V}`, where V is `passed`, `failed`, `error`, `unsupported` or `unavailable`; or `{"outcome": "refused", "reason": R}` with one of the reasons below. A host may add fields; the judge reads only these.

**The host's own input** must have that shape before anything else is done: `root` a string; `provider` and `executor` non-empty lists of strings; `obligation` an object whose `specified_by` and `targets` are lists of strings; every input an object with a string `path` and `identity`; every tool an object with a string `name` and `digest`; `platform` an object; `deadline_ms` a positive integer. Otherwise, and also when the input is not a JSON object, the check is refused with `bad-input`, and the provider is never started. Every file the obligation names must be among `inputs`, or the check is refused with `unknown-file`, again before the provider is started.

**The session.** The host starts the provider, sends `hello` (protocol `0.2`, its limits, and an `echo` string with non-ASCII and control characters), and requires a `manifest` whose `echo` is the same string. The manifest must be an object whose `capabilities` is a list of objects, each with a string `capability`, no capability named twice, the strength of `obligation.check` (where given) an object with a string `class` and a `rank` on the scale below, and whose `tools` is a list of objects each with a `name` of letters, digits, `.`, `_` and `-` only: `bad-manifest` otherwise. Every request is answered by a `result` with the same `id` (`wrong-id`), the same `capability` (`wrong-capability`) and an object `body` (`unexpected`); an `error` answer is `provider-error`. `tools` is required; a manifest without it is not read as declaring none, and a strength given as `null` is given. At the end of every check in which `hello` was sent, whether it ends in a verdict or a refusal, even one refusing the manifest, the host sends `shutdown`, gives the provider up to one second to exit as in a session, and ends every process in the provider's process group (on Unix) or job (on Windows), including those it started. A process that deliberately leaves both, on Unix by starting a session of its own, is beyond what a host can promise to end.

**Reading in a check.** Messages are read as in a session, with these differences. The deadline applies to each message the host sends or waits for, not to the whole check: a provider that stops reading cannot hold a host past it. JSON is read strictly, as the canonical encoding writes it (protocol/canonical-encoding.md): a repeated key, at any depth, is `duplicate-key`; a number with a fraction or an exponent, or an integer beyond plus or minus 2^53 − 1, is `not-an-integer`; a string holding half of a UTF-16 pair is `encoding`; and after the line has been read whole, nesting deeper than 64 is `too-deep`. Message bodies are not validated against the schemas beyond what this section names; a field it does not name is ignored, and nothing it says is acted on.

**The check.** The host sends `obligation.check` with `{"op": "start", "obligation", "inputs", "tools", "platform"}`. Each answer must have exactly one of `next` and `final`: `neither-or-both` otherwise.

For each `next`, before anything runs, in this order. Each rule is checked over every entry it concerns before the next rule is, so when two entries break different rules, the earlier rule is the reason. Within one rule, each of its clauses is checked over every entry, in the order the rule gives them. For rule 4 that is: `undeclared-tool`, then `tool-not-in-key` for the tools the program and arguments name, then `tool-not-in-run`, then `tool-not-in-key` for the entries of the run's `tools`, then `tool-digest-mismatch`. For rule 9, `input-not-in-key` before `identity-mismatch`:

1. More than 8 runs: the request for a ninth is refused, `too-many-runs`.
2. The description has its shape: an object, whose `program` is an object with a string `tool` and `path`; `args` a list; `inputs` a list of objects each with a string `path` and `identity`; `outputs` a list of objects each with a string `path`; `tools` a list of objects each with a string `name` and `digest`; `platform` an object; `cwd`, where given, a string; and `limits`, where given, an object of integers: `bad-description` otherwise. (`env` is left to rule 7, whatever its value.)
3. The run's `platform` is the one the check was asked for: `platform-mismatch`.
4. The tool its `program` names, and every tool any argument names as `${tool:NAME}` (with or without a file after it, every occurrence), is declared in the manifest (`undeclared-tool`), is among the tools the check was given (`tool-not-in-key`), and is in the run's own `tools`, so the executor pins and reports its digest (`tool-not-in-run`). Every entry of the run's `tools` is a tool the check was given (`tool-not-in-key`), with the same digest (`tool-digest-mismatch`).
5. The program's path, every input and output path, every file a `${tool:NAME}/PATH` argument places, and `cwd` pass the path check (protocol/path-check.md): `bad-path`. In `${tool:NAME}/PATH` each segment of `PATH` holds only ASCII letters, digits, `.`, `_` and `-` (`bad-path` otherwise), so a tool argument cannot carry a value after its file, as `lib/x=/etc/passwd` would. An argument holding NUL is not path-checked here; it is left to rule 10.
6. Arguments by allowlist: an argument containing any of `/`, `\`, `~`, `@`, `$`, `%`, `..`, or a character outside printable ASCII must be, exactly and whole, one of the run's input paths or one `${tool:NAME}/PATH`: `bad-path`. An argument that is not a string, or contains NUL, is left to rule 10.
7. A run description has no `env` field, whatever its value: `env-not-allowed`.
8. No output has the path of an input of the run or of the check, with ASCII letters compared without regard to case: `output-overwrites-input`.
9. Every input of the run is one of the check's inputs (`input-not-in-key`), with the same identity (`identity-mismatch`).
10. Every argument is a string without NUL: `bad-arguments`.
11. The run's inputs include every file the obligation names: `missing-input`.

The run is then given to the executor: the host starts the `executor` command once per run, in `root`, with `{"number": N, "run_key": K, "run": <the description>}` on standard input and reads one report from standard output, strictly, as messages are read: the report is the first line, ended by a line feed alone, so a carriage return before it, an empty first line or no line feed at all means no report. `N` counts from 1. `K` is the identity of `{"check": C, "run": N, "description": D}`, where C is the identity of `{"obligation": O, "inputs": I}` as the host was given them and D the identity of the description, so each run has its own key and a second run with the same description is never answered from the first. A report whose `end` is not `exited`, an executor that exits with a status other than 0 or prints no object that can be read, or a report whose `platform` is not the run's or whose `tools_ran` are not the run's `tools` (the same names with the same digests), ends the check with the verdict `error`, and the provider is not asked to interpret it; a report whose `end` is `unavailable` gives the verdict `unavailable`. A host waits for the executor at least the run's `limits.wall_ms` plus 60 seconds, however short its own deadline, and at most 24 hours; a run that states no `wall_ms` is waited for the 24 hours. A run it stops waiting for ends as `timed-out`. The host starts the executor in a process group (on Unix) or job (on Windows) of its own, and when the executor returns or is stopped, every process in it is gone. An exited run is passed back with `{"op": "run.result", "check": <id of the start request>, "run": N, "report": R}`.

For a `final`, in this order, each rule over every attachment before the next: it is an object whose `attachments`, where given, is a list of objects each with a string `path` and `identity` (`bad-final` otherwise); every attachment's path passes the path check, and the file it names is reached from `root` without following a symbolic link at any step, is a regular file and holds at most 64 MiB (`bad-path` otherwise); its bytes, hashed again, have the identity it states (`identity-mismatch`); the verdict is one of `passed`, `failed`, `error`, `unsupported` (`bad-verdict`; `unavailable` comes only from the executor's report, never from a provider); and a `passed` or `failed` verdict rests on at least one run (`verdict-without-run`), states a `strength` that is an object with a rank (`documented` < `sampled` < `bounded` < `exhaustive`) no higher than the manifest declares for `obligation.check` (`strength-above-ceiling`), and the same `class` (`strength-class-mismatch`).

Nothing may be reported as passed except in the controls, and where a run would have been dangerous it must not have started.

**How the judge reads a run.** The host reads its standard input from a private file holding the exact text of the case and writes its standard output to another, which the judge reads back up to 1 MiB; it is given 120 seconds and, if it takes longer, is ended through the judge's own handle on the process it started, and nothing else is ended. Only an answer completed with exit 0 that is one JSON object with a string `outcome` is judged. A host that could not be started, ran out of time, exited other than 0 (even after printing a valid refusal) or printed anything else gave no answer, and the case is `UNFINISHED`. So is a case whose records cannot be read: a transcript, run record or process-id file that is gone, not a regular file, too large or malformed. The judge creates those files empty, so an empty run record shows that no run was given. Only the ten cases whose curated expectation is `refused` with `bad-input` or `unknown-file` and no runs may leave the provider's transcript and process ids empty; this is read from the case, never from the answer. Processes left behind are told by the same cooperative probe and stop file as for sessions (`watch_fixture` in `tools/run_provider_cases.py`): one that acknowledges the probe is a `MISMATCH`, one whose state cannot be told is `UNFINISHED`, and no recorded id is ever signalled. Each case is named by its mode, how its run ended and a digest of its whole content, since several cases share a mode. The last line is `{"cases", "judged", "skipped", "matched", "all_matched", "unfinished", "rejected"}`, `rejected` naming each completed mismatch; a case skipped on a platform is counted as skipped, never as matched. The judge exits 0 when every judged case matched, 1 when the run completed with mismatches, and 2 when any case did not finish or none was judged.

## How a project's status is judged

`tools/run_status_cases.py --kernel <kernel> -- <command>` judges a command that reports the status of a whole project from its project file, its providers and its ledgers, and runs nothing ([decision 0034](../decisions/0034-a-kernel-runs-a-project-and-reports-its-status.md)). The reference is `python tools/project_status.py`. Each case in `project/cases.json` is a small project, with providers that answer from a file of the case, as JSON or as raw lines for answers no JSON writer makes (`project/fixture_provider.py`), and either the reason it must be refused or statuses, written by hand from the status rules, that its report must give. What the command judged, the coverage, the ledger note, what it does not serve, what nobody can check and the requests it sent its providers are compared with the reference's, as JSON text, so `0` and `false` or `1` and `1.0` are distinct. The given kernel's `scenario` command recomputes the report from the reference's scenario, which must equal what the command says it judged. Use a kernel other than the one judged so that the report is checked independently. The processes must each supply a strict JSON object. A report can carry ledger entries up to 64 levels deep (protocol/ledger.md), so the reader permits deeper nesting.

With `--variants` the judge runs the cases it generates by taking each field of the provider answers, the policy and the input of six curated cases away, giving it a value of another kind or editing lines in their project file. Each variant takes its expectation from the reference. A refusal must hold exactly `{"refused", "detail"}`, and the providers it started and what it asked them must agree with the reference's. A case that requires links or restricted permissions is skipped on systems that cannot provide them. The case "an empty root" starts the command in the project's own folder, with `PWD` set to it, after turning each argument that names a file into an absolute path. Give the command as a program followed by its file arguments.

The summary on the final line reports `cases`, `judged` (cases less skips), `skipped`, `matched`, `rejected` (names of completed mismatches), `unfinished` and `all_matched`. The judge exits 0 when all non-skipped cases match and at least one was judged, and 1 when all non-skipped cases complete and at least one differs. It exits 2 when no case can be judged, a required process cannot start, times out, exits unsuccessfully or produces unusable output, or a reference premise contradicts the fixture. Generated variants stay in the count when their reference fails.

**The command.** It is started once per case. Its standard input is one JSON object, from its first byte (`{`) to its last (`}`) or followed by exactly one line feed, with no other space, carriage return or line feed around it, read with the JSON rules of a check (a repeated key, a fraction or a non-JSON value is not read); fields the input does not name are ignored. It prints one JSON object, in UTF-8 whatever the console's encoding, and exits with status 0, whether it reports or refuses:

- In: `{"root": DIR, "project": PATH, "site": {"platform": {"os", "arch"}, "writer": W, "runner": R, "tools": [{"name", "version", "digest"}], "providers": {NAME: {"command": [argv], "code": [PATH]}}, "deadline_ms": N}, "policy": P, "policy_source": S, "ledgers": [PATH], "owner_ledger": PATH}`. Every PATH is relative to `root`. `P` is the policy in the form the status rules apply: the site reads the policy file from where it anchors it (`S` says where), checks it against [policy.schema.json](../protocol/policy.schema.json), fills in the floors the schema gives by default, and names every field it holds that no status rule applies (`tools/policy_input.py` does this for dodona). Every provider is started with its `command`, in `root`.
- Out: `{"judged": J, "report": R, "coverage": C, "policy_source": S, "ledger": {"entries": N, "torn": T}, "not_served": [{"binding", "capability"}], "not_checkable": [obligation names], "policy_not_applied": [field paths], "project_doubts": [reasons], "project_status": STATUS}`, exactly these fields, on standard output, with exit status 0, or `{"refused": REASON, "detail": TEXT}`. `detail` is for a person and is not judged. `J` is the status scenario the command judged (step 10); it carries the ledger entries, so it may nest deeper than 64, and a kernel's `scenario` command reads it whole. `R` is the last result its own status rules give for `J`, exactly what its `scenario` command answers for `J`. `project_doubts` lists, in this order and in these words, what could hide a failure the report does not show: `policy no status rule applies` (when `policy_not_applied` is not empty); `a required intent has children, and no status rule reads descendants yet` (when a required intent lists any child, defined or not); `obligations the provider could not make into checks` (when `not_checkable` is not empty); `criteria declare what no status rule reads yet: a deferred gate's limit, runs that must agree, or evidence not applicable` (when any criterion has `limit_days` or `not_applicable`, or any link has `varying`); `a ledger ends in an entry cut short`; and `a ledger the site names does not exist` (when one of `ledgers`, not the owner's, does not exist). `STATUS` is the project's status as the command states it, and what an agent reads: `R`'s, except `unknown` where `R` says `passed` or `nothing-required` while `project_doubts` is not empty.

A path below is *relative* when it is not empty, does not start with `/`, holds no `\`, no `:` and no NUL (no file's name holds one), and has no segment that is empty, `.` or `..`. *Reached without a link* means no step of the path is a symbolic link or a junction. A file's *identity* is `sha256:` followed by the lowercase hexadecimal SHA-256 of its bytes. *Sorted* means sorted as the canonical encoding sorts keys, by UTF-16 code units, each member once. The steps run in this order; the first rule broken gives the reason, and nothing after it is done.

1. **The input** has this shape, or it is `bad-input`: `root` a string naming a directory (an empty string names none, whatever folder the command was started in); `project`, `owner_ledger` and every entry of `ledgers` relative paths; `policy_source` a string; `platform` an object with string `os` and `arch`; `writer` and `runner` strings; `tools` a list of objects each with string `name`, `version` and `digest`; `providers` an object whose values each have a non-empty list of strings `command`, none holding a NUL (which no program's arguments can carry), and a list `code` of relative paths, each once, each a regular file reached from `root` without a link at any step (`bad-input` otherwise, a path a step of which cannot be looked at included, since it is not shown to be one; then every code file of every provider is read, `unreadable-file` if one cannot be, before any provider is started); `deadline_ms` an integer from 1 to 86,400,000; and `policy` an object holding exactly `required`, a list of strings (the intents that must be delivered); `min_hard_gates`, an integer of at least 0; `floors`, an object mapping kinds of act among `confirm-baseline`, `match-check`, `grant-amendment`, `close-deferred` and `change-policy` to levels among `self`, `helper`, `apart`, `tested`, `cross-make` and `credentialed`; and `not_applied`, a sorted list of strings, each once, the fields the policy holds that no status rule applies, echoed as `policy_not_applied`.
2. **The project file** must be a regular file reached without a link (or it is `bad-project`, a path a step of which cannot be looked at included), that can be read (or `unreadable-file`), in UTF-8 with no byte-order mark, and in this subset of TOML, or it is `bad-project`. No line holds a carriage return, a tab, or a character from U+0000 to U+001F or U+007F to U+009F. A line is: empty or only spaces; a comment, spaces and then `#` and anything; a header, the whole line exactly `[project]` or `[policy]`, or `[[binding]]`, `[[platform]]` or `[[tool]]`, with nothing after it; or `KEY = VALUE` starting the line, where `KEY` is lowercase letters and `_`, one space each side of `=`, and `VALUE` is a string in double quotes holding no `"` or `\`, or a list on the same line of such strings, with any spaces after `[`, before `]` and around each comma, possibly empty, followed by nothing, by spaces, or by one or more spaces and a comment. A key given twice in one table, a key before any header, and a `[project]` or `[policy]` header given twice are `bad-project`. A `[policy]` table is read for its shape only: the policy comes from the site (step 1). Each `[[binding]]` has a string `name` and `provider` and a list `capabilities`; `match`, where given, is a list of patterns. A pattern is a relative path (so it holds no `:`) whose segments hold `*`, ranges `[a-b]` of two printable ASCII characters (U+0021 to U+007E) other than `/`, `:`, `[`, `\` and `]`, with `a` no later than `b`, and any other character but `[`, `]`, `\` and `/`. Two bindings with one name are `bad-project`.
3. **What is served.** This command serves `obligation.enumerate` and `intent.index`. Every other capability a binding lists is named in `not_served` as `{"binding", "capability"}`, sorted by binding and then capability. A binding that lists a served capability and whose provider is not among the site's `providers` is `no-provider`.
4. **Files a binding claims** are the regular files under `root`, reached without a link at any step and with no path segment `.git`, that one of its `match` patterns matches: a pattern and a path have the same number of segments, and in each segment `*` matches any run of characters and `[a-b]` one character from `a` to `b`. Each is given as `{"path", "identity"}`, sorted by path. First every served binding's files are claimed: every folder under `root` that the walk enters (none named `.git`, none through a link) is listed, entries being told apart by what the listing says of them; a folder that cannot be listed, or a claimed file that cannot be read (in a folder that can be listed but not entered, too), is `unreadable-file` (a status read from part of the files would look whole). Then a file that two bindings claim for the same served capability is `overlapping-bindings`.
5. **Obligations.** For each binding that lists `obligation.enumerate`, sorted by name: a session with its provider as in a check (`hello` with a line limit of 1,048,576 bytes and `deadline_ms` exactly as the input gives it, as every request carries it too; nesting deeper than 64 is `too-deep` and an integer beyond plus or minus 2^53 − 1 is `not-an-integer` however deep or long, the manifest's rules, strict reading, `deadline_ms` per message, `shutdown`, every process ended). A provider whose command cannot be started is `provider-not-started`. A session rule broken gives the reason the host checks give for it (`bad-manifest`, `provider-error`, `deadline`, `wrong-id`, `too-long` and the rest); what a provider writes after its answer is not read. When one answer breaks two of these rules at once, which reason is given is not judged yet. The manifest's `name` and `version` must be strings and its `protocol` the one `hello` offered, `0.2` (`bad-manifest`), and its `name` must be the binding's `provider` (`provider-mismatch`). One request, `obligation.enumerate` with `{"binding", "definitions": [], "files"}`. Then, each rule over every obligation of the answer before the next rule: the answer's `obligations` is a list, its `rejected`, where given, a list of objects each with a string `name`, and each obligation an object with a non-empty string `name`, a string `kind`, lists of strings `specified_by` and `targets`, a string `expect`, an object `config`, a string `defect_of` where given, and `inputs` (`bad-answer`); `inputs` is a sorted list of strings, each a path among the files given (`bad-inputs`); every path of `specified_by` and `targets` is among `inputs` (`unknown-file`); no obligation name has been given before, by this binding or an earlier one (`duplicate-obligation`). The names in `rejected`, of every binding, are `not_checkable`, sorted: a project with an obligation nobody can check is not shown as having none.
6. **Keys.** Each obligation's preimage ([core-key vectors](vectors/core-key.json)) is `{"obligation": the identity of {"binding", "name"}, "kind": "check", "inputs": {"specified_by", "targets", "closure", "tools", "config", "expect"}, "provider"}`. Let F be the files the provider listed in `inputs`, each with its identity. `specified_by` and `targets` are the sorted identities of the files of F whose paths the obligation lists there (two files with the same bytes give one identity); `closure` is the sorted identities of `{"path", "identity"}` for every file of F; `tools` is the site's tools that the provider's manifest names among its `tools`, as `{"name", "digest"}`, in the order the site gives them (so a tool pinned for another provider changes no key of this one); `config` is the identity of the obligation's `config`; `expect` is its `expect`. The provider is `{"name", "version": V + "+" + CODE + "+" + R, "protocol"}`, with `name`, `V` and `protocol` from its manifest, `R` the site's `runner`, and `CODE` the first 16 hexadecimal digits after `sha256:` of the identity of an object mapping each path of the provider's `code` to the lowercase hexadecimal SHA-256 of its bytes.
7. **Intents.** For each binding that lists `intent.index`, sorted by name: a session as in step 5, and one request, `intent.index` with `{"binding", "files", "obligations"}`, where `obligations` lists every obligation of step 5 as `{"binding", "name"}`, sorted by binding and then name. The answer's `intents` is a list and its `rejected`, where given, a list of objects each with a non-empty string `path`; each intent is an object with a non-empty string `name`, a string `text`, an `owner` object with a string `id`, a `worker`, where given, of the same shape, a list `children` of non-empty strings, and a list `criteria` of objects each with a non-empty string `id`, a string `statement`, a string `gate` and a list `links` of objects each with a string `binding` and `obligation` (`bad-answer`). A non-empty `rejected` is `intent-unreadable`: a status read from part of the intents would look whole. Then, over the intents of every binding, each rule over every intent before the next rule: a criterion id given twice in one intent is `duplicate-criterion`; a link whose binding and obligation are not one of step 5's is `unknown-link`; an intent name given twice is `duplicate-intent`; a name listed as a child by two intents, whether or not an intent has that name, is `two-parents`; and following parents from an intent that comes back to it is `intent-cycle`. Each intent becomes `{"owner": owner.id, "worker": worker.id or "", "children": children sorted, "words": text, "criteria": {id: {"words": statement, "gate": gate, "checked_by": the obligation of each link, sorted}}}`.
8. **Ledgers.** The owner's ledger must be reached from `root` without a link at any step and, if it exists, be a regular file (`owner-ledger-link`); only its entries of kind `act` are read. Then each of `ledgers` in turn, which may be reached through links; one that is the same file, as the operating system identifies files, as the owner's ledger or a ledger read before it (a path spelt in other letter case, or a hard link, included) is skipped entirely. Of these ledgers only entries of kinds other than `act` are read: acts count from the owner's ledger alone. A ledger already read, as the operating system identifies files, is not read again. A ledger that exists and is not a regular file, or is not as [the ledger format](../protocol/ledger.md) requires, is `corrupt-ledger`; one that cannot be read is `unreadable-file`. The owner's ledger is read exactly as strictly as any other. A ledger, the owner's included, is *absent* when its path leads, through folders that can be entered and no link to nothing, to no entry: it has no entries. A link to nothing at any step of its path, or a folder on its way that cannot be entered, makes it `unreadable-file`, never absent: an unreadable ledger may hold a failure. `ledger` gives how many entries were read and whether any ledger, the owner's included, ended in an entry that was cut short.
9. **Policy.** `required` and `floors` are the policy's, and `min_hard_gates` the policy's but at least 1 (an intent with no hard gate is never delivered, decision 0018); a kind of act `floors` leaves out is read by the status rules as `self`. The policy schema has no place yet for trusted writers, attestors or makes, so `trusted_writers` and `makes` are empty lists and `attestors` an empty object.
10. **What is judged.** `J` is `{"kind": "status", "name": "this-project", "self": {"writer": W, "platform": OS + "/" + ARCH}, "policy", "obligations": {name: {"preimage"}}, "intents", "steps"}`, whose steps are one `{"do": {"append": {"kind", "body"}}}` for each entry read, in order, and then one step that names nothing, `{"do": {"set_gate": {"intent": "", "criterion": "", "to": "hard"}}}`, so that a project with an empty ledger has a report too. No intent is named `""` (step 7), so that step changes nothing. An obligation's name is data, kept exactly as its provider gave it: a name such as `__proto__` is a key of `J`'s `obligations` and of the report's like any other (case "a passed result counts under any obligation name").
11. **Coverage** says where each intent tree's hard gates sit (decision 0030). A criterion is hard as the status rules count it: any gate other than exactly `soft` or `deferred`. An intent's parent is the intent that lists it among its children, and its root is reached by following parents (step 7 rules out two parents and cycles). For each intent, `C.intents[I]` is `{"own_hard", "subtree_hard", "root", "tree_hard", "floor", "floor_met_only_over_tree"}`: its own hard criteria; those of it and every intent below it, each counted once and only if defined; the root; the root's `subtree_hard`; the floor, `min_hard_gates` but at least 1; and whether it is not its root and its `subtree_hard` is below the floor. `C.thinnest` maps each root to the intent of its tree with the fewest hard criteria of its own, the first in sorted order on a tie.

## How a project's run is judged

`tools/run_run_cases.py --kernel <kernel> -- <command>` judges a command that does what the status command does and then checks every obligation that has no current result, sends the runs to the site's executor in batches, records each verdict in a ledger, and reports as the status command does ([decision 0034](../decisions/0034-a-kernel-runs-a-project-and-reports-its-status.md)). The reference is `python tools/project_run.py`; a kernel's `run` command is judged the same way. Each case in `project/run-cases.json` is a small project with a provider that enumerates, takes checks through the runs it describes and gives verdicts as the case scripts them (`project/fixture_provider.py`), and an executor that answers batches as the case scripts them (`project/fake_batch_executor.py`). Most of what is judged does not come from the reference: the command's report must equal what its own `status` command reports straight afterwards, a second `run` must check exactly what the first left unrecorded (and send the executor nothing when that is nothing), the counts must add up to the obligations, every run sent must be a run its provider described, unchanged, and carry the number and run key recomputed from what its provider was asked, a refused run must leave every file of the project as it was, and what each case writes by hand (the number of batches, the verdicts recorded, the statuses) must hold. What it judged, asked its providers and sent before a refusal is also compared with the reference's.

The run judge needs completed JSON answers from the commands the case uses. A launch failure, timeout, nonzero exit, invalid JSON, or a reference or independent scenario that cannot establish the fixture's expected behavior leaves that case unfinished. A valid named refusal is a completed answer with exit 0. A completed difference in the report, recorded evidence, or named refusal is a mismatch. The last line reports `cases`, `judged`, `skipped`, `matched`, `all_matched`, `rejected` and `unfinished`. The judge exits 0 for a complete match, 1 for completed mismatches, and 2 if a case was unfinished or none could be judged. Platform skips are counted separately.

**The command.** It takes the status command's input with two more fields, `ledger`, the relative path of the ledger verdicts are appended to, and `executor`, a non-empty list of strings, the command that runs a batch, and a third where wanted, `transcript`, a relative path that names no ledger, no ledger's lock (`<ledger>.lock`, the owner's ledger's included) and not the project file (compared the same way) and is not yet there, in a folder that is there, reached without a link: when the run reports, it writes there, as a new file, a JSON list of every message it sent to a provider and read from one, in order, each as `{"to": "provider" or "kernel", "message"}`, which `tools/check_transcript.py` validates against the protocol's schemas. Standard input, refusals, output and exit status are as for the status command, and its output has one more field, `counts` (below); its other fields are the status command's as they are, `not_served` included. A transcript that cannot be written after verdicts are recorded is `transcript-not-written`; the verdicts stay recorded.

Steps 1 to 9 are the status command's, with these additions to step 1: `ledger` must be one of `ledgers` (so what this run records is what the next run reads), must not be the owner's ledger, by path compared as a disk that ignores case and Unicode normalization compares names (NFC of the case-folded NFC) or, where both exist, as the same file, and must be reached without a link (`bad-input`); `executor` must be a non-empty list of strings, none holding a NUL (`bad-input`); `transcript`, where given, as above (`bad-input`); and no segment of `ledger` or `owner_ledger`, nor, where `transcript` is given, of `transcript`, of any entry of `ledgers` or of `project`, may end in a dot (U+002E) or a space (U+0020), each where it is a relative path (`bad-input`): a disk that drops them ([decision 0009](../decisions/0009-platform-order-and-portability-rules.md)) takes `owner.ledger.` for `owner.ledger`, which no comparison of names above sees. That rule is read from the strings alone; it is not the whole path check, and the status command's input keeps its own rules. All of these are checked first, before the status command's own checks of step 1 (those that need `root`, only when it is a folder), and so before any provider is started. Step 5 keeps the session of each binding that lists `obligation.check` open for the checks, so the provider that enumerated, with the code and manifest measured then, is the one that checks. Then:

10. **Plan.** The status rules are applied to the scenario of step 10 of the status command, and each obligation whose status is `unknown` is to be checked; one whose status is `passed`, `failed` or `conflict` has a current result and is reused, and nothing is sent for it. The obligations in `not_checkable` and not among the obligations the provider listed are not checked; a name both listed and rejected is checked as listed (the rejection still makes the project's status unknown). Obligations are taken sorted by binding and then name.
11. **Checks.** Each check runs on its binding's session from step 5, held open for the whole run. An obligation whose binding does not list `obligation.check`, or whose provider's manifest does not offer it, is counted as `refused`. Each check is started as the host checks give it (`{"op": "start", "obligation", "inputs", "tools", "platform"}`), where `obligation` is the obligation as enumerated with its `binding` and without `inputs`, `inputs` the files of F with their identities, `tools` the site's tools that the provider's manifest names, as `{"name", "version", "digest"}`, and `platform` the site's platform. Every rule of "Host checks", 1 to 11 for each run and the rules for a `final`, applies, with the same reasons; a check a rule refuses ends with no verdict and is counted as `refused`. A reason that says the session itself broke (`deadline`, `closed`, `framing`, `too-long`, `encoding`, `malformed`, `not-an-integer`, `duplicate-key`, `too-deep`, `wrong-id`, `wrong-capability`, `unexpected`, `provider-error`) puts every check on that session in doubt: the whole run is refused with that reason, and nothing is recorded.
12. **Batches.** The runs every open check asks for at one time form one batch. The executor command is started once per batch, in `root`, in a process group (Unix) or job (Windows) of its own that is ended when it returns, with `{"runs": [{"number", "run_key", "run"}]}` on standard input, in the order the checks were started; `number` and `run_key` are as in the host checks. Its answer is read once the executor has exited and its standard output has closed (a process it started that keeps that output open keeps the batch waiting, within the wait below). It must exit with status 0 and print one JSON object, read strictly (so, as everywhere, no fractions and no key twice), as its first line, ended by a line feed alone, with no byte-order mark: `{"ended": true, "reports": [{"run_key", "report"}]}`; anything after the first line is not read. A batch whose executor cannot start, exits otherwise, prints nothing that can be read, or whose answer is not an object with `ended` `true` and a list `reports`, gives every check with a run in it the verdict `unavailable`. A batch whose reports include an item that is not an object with a string `run_key` of the batch and a `report`, or name one `run_key` twice, gives every check with a run in it the verdict `error`. A run with no report in an ended batch, or whose report is not an object, gives its own check the verdict `error`. Each other report is then read as the host checks read one, and passed back to the provider: one at a time, in the order the checks were started, each provider's answer read before the next report is sent, and nothing sent on a session after it has broken. A check that asks for another run gets it in a later batch, up to eight runs. The executor is waited for at least the longest `wall_ms` of the batch plus 60 seconds (a `wall_ms` below 0 is read as 0), and at most 24 hours; a batch with a run stating no `wall_ms` is waited 24 hours. A batch not answered in that time gives every check with a run in it the verdict `error`.
13. **Record.** For each check, in the order checks were started, whose verdict is `passed` or `failed`, each input file is read again and must still have the identity it was keyed with; one that changed or cannot be read makes the verdict `error`, counted as such and not recorded. For each that keeps its verdict, one entry of kind `evidence` is appended to `ledger`, all in one append, as `ledger-append` appends: any folders on the ledger's path that are not there made, the lock beside the ledger taken (waited for up to 60 seconds), an ending cut short cut off, each entry added as one line after the last and written to disk, the lock released: `{"obligation": name, "preimage", "core_key": its identity, "platform": OS + "/" + ARCH, "verdict", "writer": W, "strength": the final's strength, "level"}`, with the preimage of step 6, and `level` the final's rank read as the host checks read it (`documented` as `asserted`, `sampled`, `bounded`, `exhaustive` as `proven`). The strength and the level are the provider's own word, bounded only by what its manifest declares: nothing in a run shows that a check is as strong as its provider says. No other verdict is recorded. A ledger that cannot be appended to (its lock held for 60 seconds, the ledger corrupt, a write failing) is `ledger-not-written`, and nothing after it is done; the verdicts of that run are lost, and the next run checks those obligations again.
14. **Report.** The ledgers are read again, as in step 8, and the output is made as the status command makes it, from what is now in them, with `counts`: `{"obligations", "reused", "checked", "passed", "failed", "error", "unavailable", "unsupported", "refused", "not_checkable"}`, where `obligations` counts the obligations the providers listed (a rejected name not listed is not one), `not_checkable` the length of `not_checkable` (a name both listed and rejected counts there too), `reused` and `checked` add up to the obligations, and the verdicts and `refused` add up to `checked`. A refusal here (a ledger that has become unreadable or corrupt during the run) comes after step 13: the verdicts appended stay recorded.

A run with nothing to check starts no provider session for checks and no executor.

## Two kernels compared

`tools/kernel_differential.py --a <kernel> --b <kernel>` replays every scenario with its steps drawn again at random, repeated, dropped and reordered, and requires the two kernels to give the same answer in full, not only in the fields a scenario names. A difference, or an input neither answers, becomes a scenario. Agreement is not correctness: two kernels can be wrong the same way.

`tools/run_attest_check.py -- <kernel> scenario` has a kernel grade act records whose check values are made at test time by the reference signer, `tools/attest.py`, and requires it to stop accepting them once the record is changed. The kernel grades all seven records in one run, which exits 0. A completed grade that differs, and a per-case answer that is missing or malformed (output that is not JSON included), is reported as `MISMATCH` under the case's name. A kernel that could not be started, timed out, was ended by a signal or exited with a status other than 0 graded nothing, and every case is `UNFINISHED`; so is a case whose check by the signer itself did not finish or disagrees with the verdict the fixture expects, which is a failure of the judge, and a run whose records the fixture and signer could not make. The last line is `{"cases", "matched", "all_matched", "unfinished", "rejected"}`, `rejected` naming each case that did not match. The judge exits 0 for a complete match, 1 for a completed run with mismatches, and 2 for a run that did not complete or in which no case ran.

`tools/run_harness_check.py -- <kernel> scenario` runs the reference harness, `tools/harness.py`, which really starts a checker in a directory holding only what it was given. With `harness/checker_reads.py`, which reads its files, the kernel must grade the signed record `cross-make`, `tested` or `apart` according to what the harness was given. With `harness/checker_nods.py`, which agrees with everything, the known-wrong case exposes it and the grade stops at `apart`. A record changed after signing, signed with a key policy does not list, or written without the harness, stays at `helper`. The judge reports eight outcomes: the seven records the kernel grades and the known-answer control, "the known cases tell the real checker from the one that agrees with everything", which is judged on the harness alone. It makes its records in strict mode, so a checker that could not start, timed out, exited other than 0 or gave no `agreed` or `refused` is never read as a refusal. A kernel that did not finish, a control that did not hold, or a checker grade that is not the fixture's is unfinished (exit 2), never a mismatch. Only a completed wrong grade is a mismatch, named in `rejected` (exit 1). The ordinary harness CLI is unchanged.

## Rules for the kit

- A scenario is added before the behaviour it tests, and is committed before any kernel that will be judged by it.
- Expected results are written by hand from the documents and the models, never produced by a kernel.
- Generated variants take their expected answers from a reference, which can be wrong. Where a reference contradicts the text, the text decides: the reference and the answers made from it are corrected, a kernel is never bent to the reference, and the disagreement is recorded in the review log.
- Two kernels that both pass the whole kit and still disagree on some input mean the kit is missing a scenario; the disagreement becomes one.
- Hostile names and bytes are stored as escaped data inside the vectors, never as real files, so the kit can be checked out on every platform.

## Not yet in the kit

- The evidence entries and the status report in the kit are smaller than `protocol/evidence-record.schema.json` and `protocol/status.schema.json` describe. Those schemas are the target, and nothing validates a kernel's output against them yet.
- The run command's cases (`project/run-cases.json`) use a fake executor. Not judged there: whether the run takes and waits for the ledger's lock (no case holds it); an executor that lies within the report format; the lock and `fsync` against a crash; the executor's working directory and process group; the wait beyond six seconds (a host waiting at least that long but less than `wall_ms` plus 60 seconds passes); an executor that cannot start; an executor's answer of any length (the reference reads all of it); a negative `wall_ms`; the order of runs within a batch, except on refusals; a conflict, which is reused and never checked again.
- What the run command does not detect: a file edited during a run and put back before step 13 (the report names no input identities, so nothing binds what the executor ran to the key); a provider's code changed between step 1, where it is hashed, and step 5, where the provider starts; attachments, whose rules are judged only in the host checks.
- Host rules judged through the run command only where a case gives them: environment, paths, outputs written over inputs, undeclared tools, tools outside the key, malformed descriptions and arguments are judged in the host checks. An input read again before recording follows links; a run's ledger at a path a binding claims becomes project input, as a transcript there does.
- Trust boundaries the run command does not close: a provider runs as project code in the root and can append to the run's ledger itself, and `writer` is not authenticated; a transcript written where a binding matches becomes project input for the next run; `kind` and `defect_of` are not in the key, so changing only them keeps old results.
- Status cases compare what a command judged with the reference; statuses are written by hand only in the cases that name them. No status rule reads a deferred gate's limit yet.
- The two kernels' `status` commands are not compared with each other on inputs no case gives, as their `scenario` answers are.
- A process that deliberately leaves a provider's or an executor's process group or job; no host is judged on ending it.
- The wait for an executor is judged only to within two seconds of `wall_ms`, not to the full 60-second margin the text requires: judging that would add a minute to every run of the kit.
- The two kernels' `session` and `check` commands are not compared with each other the way `tools/kernel_differential.py` compares their scenario answers; they are compared only through the cases above, so an input no case gives can still get two answers.
- Three attachment cases (a pipe, a link out of the project, a link at an inner step) cannot be made on Windows and are reported there as skipped, not matched.
- Whether sending counts against the deadline is judged only where a write can block: a host whose writes never block the clock (Node's streams buffer them) passes `stops-reading` on the read deadline alone.
- Anything not modelled: the ledger's crash behaviour, time limits, varying checks, executors, the lock, more than one level of child intents.
- The intent and attempts scenarios take a claim and its source as given. Working both out from an act record is in the acts and status scenarios.
- Rules that are written above and have no scenario yet: `min_hard_gates` below 1 in a tree, which is treated as 1 as everywhere else; a floor missing from policy. Both kernels were written from the same sentences, and nothing checks they read them the same way.
- What happens when a ticket name is taken a second time. The contract does not say.
- Rules written above with no scenario or vector yet: a set in a core-key preimage whose order differs between UTF-8 bytes and UTF-16 code units (the members are identities, which are ASCII, so no valid preimage can show it); an unknown field inside `inputs` other than `platform`; a ledger entry or an append whose `kind` is the empty string; an append whose `body` is null; an evidence field of the wrong type; an act whose `started_by` or `make` has the wrong type.
- The status scenarios added after the second review still use few shapes: no scenario has children that are themselves intents in the scenario, and only one has a floor above `helper`.
- The levels above `helper` in the kit describe what a kernel must do when a harness vouches for an act. No harness that an agent cannot reach exists yet, so they are not reachable in practice today.

Each byte cut in the torn-ledger fixture uses its own ledger path. The two writers still share a ledger, and their lock wait ends before the process deadline so the judge can record a completed refusal. The unreadable-gate mutation now targets an edit. The scenario for an unreadable starting gate still runs with the same expectations.
