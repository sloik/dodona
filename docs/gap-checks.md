# Gap checks

The rule: **a gap that is found becomes a check.** When a review, a mistake or a run shows that something could be wrong without anyone noticing, a check is added to `tools/check_repo.py` so the same gap cannot open again unseen. A check is added with the gap that caused it, and is first seen to fail.

These checks need no model checker. They run on every pull request on macOS, Linux and Windows, and on the project's own runner on every change to `main`.

## Documents that follow the code

The usual way a document here goes wrong is quiet: code or data changes and the text that describes it does not. `tools/check_docs.py` holds these checks, so `tools/check_repo.py` does not grow further; `gap_documents_follow_the_code` runs them on every platform. Each compares what the code or data says with what the documents say, in both directions where both can be read, and names the file and what to update. When they were first run, the checks of usage lines, the tool list, the decision index and the kit's index found real drift, fixed in the same change; the others found none, and are there so that the next change cannot bring any.

| Check | The gap behind it |
|---|---|
| `docs_map_covers_every_file` | New code could arrive that no document is bound to. [doc-map.toml](doc-map.toml) names, for every file that is not Markdown, the documents that describe it or why none does: exactly one entry per file, and every pattern must match something |
| `docs_usage_matches_the_parser` | Tools gained flags their usage lines did not show (`--policy-ref` in three tools, four flags of `check_models.py`, `--plan`, `--ledger`), and one usage line showed a flag the tool does not have. A tool's flags and subcommands are read from its source without running it; a flag that cannot be read that way fails |
| `docs_commands_name_real_flags` | A document or workflow could show a tool started with a flag or subcommand it no longer has, or a tool that is gone |
| `docs_every_tool_is_listed` | Four tools in `tools/` were named in no document at all. [tools/README.md](../tools/README.md) lists every tool with what it is for |
| `docs_decision_index_matches_the_records` | Two decisions were listed as owner direction in the index while their headers did not say so. The index must match each record's header (title, status, direction), each heading its header, and a decision that amends or supersedes another must be linked from it; what a decision governs and every decision number named anywhere must exist |
| `docs_links_and_anchors_resolve` | A link to a heading that was renamed points at nothing, and GitHub shows no error for it |
| `docs_named_paths_exist` | A document can name a file in code type that was moved or deleted. Paths meant not to exist are listed in the map with the reason, and an entry fails once the path exists |
| `docs_protocol_matches_the_schemas` | A schema, capability, kind of message or error code could be added without the protocol's README or the provider guide knowing |
| `docs_kit_index_matches_the_kit` | The kit's 'What is here' missed five files, among them the misbehaving checker and the tool-tree vectors. It must list everything in `conformance/`, and every kind of scenario needs its section of rules |
| `docs_counts_match_the_repository` | The README counts scenarios, vectors and models; a new one would leave the count stale. The models' README must list every model |
| `docs_every_check_is_listed` | A check whose reason is lost gets deleted by mistake |

Drift a check finds that cannot be fixed now is listed under `[[known]]` in the map, word for word, with the reason, and the entry fails once the drift is gone. Two are listed: `tools/host.py`'s usage does not show its `check` command or `plan`'s `--policy-ref`. That file is part of every model check's key, so showing it would make all kept results run again; it is shown with the next change that touches the file anyway (branch `kernel-run`). The first entry, a usage line of `tools/check_states.py` without `--settings`, was removed once main showed the flag.

### A change must bring its documents

`python tools/check_docs.py diff --base REV [--head REV]` judges one change, and CI runs it on every pull request into `main` and every push to `main` ([docs.yml](../.github/workflows/docs.yml)), as the job `documents follow code (judged by main)`. **It is a gate only where `main` requires it**, through a ruleset or branch protection that lists the job; without that, it reports and blocks nothing, and a change can be merged while it fails. The jobs of [checks.yml](../.github/workflows/checks.yml), `tools/check_repo.py` and `check_docs.py self-test` among them, run the pull request's own code, so they prove only what that code does: a pull request can change a check and the check it changed passes. Only this job is judged by `main`'s copy of the checker. A required check is matched by its name, so the job's name is distinctive and the job fails if any other workflow of the change defines a job that could be shown under its id or name (a name GitHub computes, or a plain name GitHub extends with matrix values, included), gives its token permission to post checks or statuses, or cannot be read; and if the judging workflow, as the change has it, runs on any event but `pull_request_target` and pushes to `main` only (`check_docs.py jobs`). Workflows are read with a YAML parser (ruamel.yaml 0.18.10, MIT, a pure-Python wheel kept in `.github/vendor/` and installed from there with no package index, checked against the hash in `.github/yaml-reader.txt`, so no run depends on PyPI being up), so anchors, aliases, tags, escapes, flow style and block scalars are resolved as a YAML parser resolves them (whether GitHub's reading differs from it in some corner is not shown); without the parser the check cannot run, which is never a pass. A check run created through the API by a workflow without that permission, or a reusable workflow from elsewhere, is not looked into. The repository's default token can only read, so posting a check result needs that permission written out. The ruleset should also pin the required check to the GitHub Actions app, so that a status posted from outside a workflow does not count. A change to a file under a rule of the map needs a change of substance (more than spacing or line endings) to one of that rule's documents in the same change, which must still be a regular file with something in it afterwards: deleting a document, renaming it away, emptying it or replacing it with a link does not count as updating it. If none has to change, a commit message of the change must carry the line

```
Docs-unchanged: <rule id>: <why no document has to change, in at least six words>
```

The line goes in a commit message, not the pull request's description. Waivers are read from the commits a change brings. Merge commits and rebase merges keep those commits, so the push to `main` is judged as the pull request was. Squash merges are allowed too, and keep the waivers only because the squash message is set to the commit messages; a squash whose message drops the line turns `main` red. Only a line that starts exactly `Docs-unchanged:` is a waiver. It is the author's own word, which is `self` in the terms of [decision 0024](../decisions/0024-separation-is-graded-not-enforced.md): the check prints it as that, for whoever reviews the change, and it grants nothing. A waiver counts for a rule the change triggered and only with a reason of at least six words. A waiver that is not needed, names no rule, or is malformed is printed as a note and does not fail the change, because commit history keeps old mistakes for ever.

A change is judged by the checker as it is on `main` and by the map as it is both where the change branched off and on `main`, so neither a change to the map nor a change to the checker loosens how the change itself is judged by this job. `checks.yml` runs the repository-wide checks as the change has them, so a change can switch them off there; this job therefore runs `main`'s checker over the whole repository as the change leaves it as well (`check_docs.py whole`), on the change's files read as git objects from the trusted checkout (links and submodules left out), never written out, so that nothing in the change is taken for git's own configuration and its `.gitattributes` cannot hide a file; the checker parses code and never runs it. For a pull request the workflow runs as it is on `main` (`pull_request_target`), takes `main` as it is now as the base, checks out only that commit, fetches the pull request's commits as git objects, and the base's checker reads them with git without checking them out or running anything from them. A base without the checker is reported as not judged only if it is no later than the last commit of `main` before the checker existed; any later base without one fails. A change to the checker, to `docs.yml`, to CODEOWNERS, to the YAML parser's wheel or the list that pins it (`.github/vendor/`, `.github/yaml-reader.txt`), or to any `[[rule]]` of the map requires owner review. A prior exact review can satisfy the rule-change check. Other judging changes retain the owner-review failure. Nothing checks that it was the owner who merged: the owner can bypass the ruleset, and anyone with the owner's token is the owner here. Once merged, the push to `main` notes such a change, and an exception the owner merged with it, instead of failing again (`--merged`). A change is judged against the map at its merge-base with `main`, so a change behind `main` is not blamed for entries `main` gained since; a file the change touches is also bound by any `[[rule]]` `main`'s map binds it to, so branching off before a rule was added does not escape it. A file new to the map must be bound by a `[[rule]]` the change brings; an `[[exempt]]`, `[[absent]]` or `[[known]]` entry the change adds fails it, because that would be the change excusing itself (rule 8 of [AGENTS.md](../AGENTS.md)): the owner adds such an entry, in a change of its own or by merging over the failure. [CODEOWNERS](../.github/CODEOWNERS) names the owner for these files, but enforces no review: the owner opens the pull requests, so a code-owner review never applies. Any change of substance to any one of a rule's documents satisfies the rule, so each rule names only the documents that describe its code specifically.


An exact rule review already recorded on protected `main` can satisfy the rule-change check. The trusted checker compares the immutable PR head, its merge base and the two map digests. It also verifies that the current map still matches the reviewed baseline and that the approval record on `main` is accepted. Changes under the owner-approval directory are themselves judging changes and need owner review. Only the matching rule-change findings become notes. The same workflow still runs the whole-tree check and judges changed documents, protected files, exemptions, known drift and the PR description. [Owner approval for PR 40](../decisions/owner-approvals/0040-documentation-bindings.md).

With no usable base (none given, all zeros, missing from the history), the check says it could not run and exits with 2, which is never a pass. A push to `main` whose previous commit is no longer in the history, as after a force-push, fails with a message saying it must be judged by hand. A change that moves nothing but pinned versions in workflows is not judged for documents: `check_docs.py pins-only` reads the change and requires every removed line to be replaced, in its place, by one pinning the same action of the same owner and repository at another full commit, never a branch or tag, or a runner of the same system at another version, with no line only added or removed. On a pull request a pin moved in `docs.yml` is not taken for a pin update: it fails as a change to how changes are judged, so the owner merges it; once merged, the push to `main` takes it as a pin update, so `main` does not turn red. A full commit is not shown to be in the action's own repository: a commit that exists only in a fork resolves under the same name. For a pull request it must also come from the automatic updater; a push to `main` is judged on the content alone, so a merged update does not turn `main` red.

A pull request's description must also have a `## Verified` section naming what ran to completion and what it gave, and a `## Not verified` section saying what did not run or was not finished, which may be just "Nothing." ([the template](../.github/pull_request_template.md)). An empty section, a comment or a placeholder such as TODO does not count, nor does a heading inside a code block. This is rule 4 of [AGENTS.md](../AGENTS.md) applied to the description a reviewer reads first.

### Each check is seen to fail

`python tools/check_docs.py self-test` plants, in a copy of the repository held in memory, a fault each check exists to catch, and requires that check to report it: an undocumented flag and a documented flag removed, a subcommand added, a workflow using a flag the tool does not have, a tool with no row, an index title that differs from its record, an amended decision that does not link back, a renamed heading, a deleted file still named, a schema, capability or message kind the documents do not know, a kit file not indexed, a scenario not counted, a check not listed, and a `[[known]]` entry for drift that does not happen. It requires each check to be clean on the repository as it is first, so a planted fault proves something. Each must be reported for the reason planted, not some other. It then judges made-up changes against the real map (a code change with no document, with an unrelated document, with a short, malformed or misnamed waiver or one not at the start of its line, old waiver mistakes where none is needed, a new file exempted by the change that adds it, known drift added by the change it excuses, among others), the description rule, which lines count as pinned versions only, and one throwaway repository end to end through git: a document changed only in its line endings does not count, a waiver in a commit message is honoured and shown, a base missing from the history is refused, and a change that moves its own file from a rule to an exemption is still judged by its base's rule. `tools/check_repo.py` runs all of it except the throwaway repository, which CI runs as a step of its own on every platform.

More checks run as their own tools in CI, because they need to build or install something:

| Tool | The gap behind it |
|---|---|
| `tools/check_examples.py` | Validates the provider guide examples, project intent criteria and offline lock fixtures. The controls exercise deferred limits, criterion IDs and platform pin uniqueness |
| `tools/kit_adequacy.py` | A kit that no defective kernel fails proves nothing. Each planted defect must be rejected |
| `tools/path_differential.py` | Two implementations of the path check written from one document could disagree unnoticed |
| `tools/run_check_cases.py` | The rules a schema cannot express were prose. A checker that breaks each one in turn must be refused by the host, and nothing recorded as passed. It judges any host command from what the provider and the executor record: runs, run keys, hello's protocol, limits and echo, every request's capability, the start request, the reports passed back, compared type for type, and the closing shutdown. A host written to forge those records is beyond it |
| `tools/check_transcript.py` | The first real provider sent three kinds of message its own schemas refused, and nothing noticed until a recorded session was validated |
| `tools/run_ledger_cases.py` | A ledger entry cut short by a crash, or two writers at once, could lose or corrupt a record silently |
| `tools/run_ledger_cases.py`, again | The ledger judge changed bytes only where the chain of entries would notice, so a reader that compared neither the length nor the checksum passed. Twenty-four whole files now break one thing each |
| `tools/gen_wrong_types.py` | Two kernels disagreed on steps whose values had the wrong type, and the comparison tool never tried such values. Six scenarios repeat each step with one value of the wrong type, which must change nothing |

| `tools/run_attest_check.py` | Check values in the kit were made once by the kit's author. A kernel must also accept ones made now and refuse them once the record is changed |
| `tools/kernel_differential.py` | Two kernels can both pass the kit and still differ where the kit does not look. On its first run it found a step order the contract said nothing about, on which one kernel crashed |

The judge that decides whether a model run matched its expectation has its own tests in the same file, for the same reason: it once misread a correct result, and it must never turn an unfinished run into a pass.

Known gaps with no check yet are listed as open in the review logs under `docs/reviews/` and as unmodelled claims in `spec/CLAIMS.md`.

What this does not do, besides the above: a new tool, a new workflow, or a rename outside a `**` pattern needs a changed `[[rule]]` and owner review; a branch forked before `docs/doc-map.toml` existed cannot be judged until `main` is merged into it; an empty HTML comment added to a document counts as a change of substance to it; `.md` files are never judged as code, the criteria in `intents/*.md` and `spec/CLAIMS.md` included; whether a squash merge's message keeps a `Docs-unchanged:` line exactly at the start of a line is not checked. The usage check reads a tool's source as Python would and fails a tool it cannot read so (another declared encoding, or code that does not parse); it still cannot see a flag added through an alias (`add = p.add_argument`) or `getattr`, or one in a tool that runs `main()` with no `__name__` guard and no `sys.argv`, and it reads only regular files, so a tool written as a link is not checked. A pull request into another branch whose own `docs.yml` has a job of this name could post a passing check of this name on the same commit; only a ruleset that requires this workflow, or one that limits who may push branches, closes that.
