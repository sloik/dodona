# Review of draft 0.1

Date: 2026-11-17. Draft 0.1 of the architecture was given to five reviewers working independently. Each saw only the repository and a rubric, not the author's reasoning, and each had to back every finding with a concrete failure scenario. The reviewers were AI agents run with different personas; this is a design review, not a proof, and reviewers of one lineage share blind spots.

| Reviewer | Angle |
|---|---|
| A | Plugin contracts: can two different real tool stacks both fit without changing the kernel? |
| B | Formal methods: is "verified" claimed more strongly than the model supports? |
| C | Cross-platform reproducibility: macOS, Linux, Windows |
| D | An outside agent trying to write a provider and to drive dodona from the documents alone |
| E | Security, bootstrap trust and failure modes: every route to a false pass |

60 findings were returned, many overlapping. Each was read against the documents before being acted on, and none was dismissed as wrong. What was changed is in the first table. What was accepted and not yet acted on is in the two lists after it.

## What changed in draft 0.2

| Finding | Raised by | Change |
|---|---|---|
| Obligations had no source, identity or ordering; "target" and "specification" were undefined | A, D | New [data model](../../MODEL.md): node and edge types, obligations enumerated by the provider with stable names, a new `obligation.enumerate` capability |
| No way to tell "safe" from "nothing ran"; no project-level result | D | Obligation and project status defined; `nothing-required` and `unknown` are never a pass |
| A pass outranked a failure recorded for the same inputs | E, B | New `conflict` status; model property `NoPassOverFail` with a planted defect |
| The agent being judged could lower the bar and get an honest pass | E | New decision [0014](../../decisions/0014-policy-is-separate-from-configuration.md): policy separate from configuration, compared against a reference |
| A hand-written record with a valid hash would be trusted; crash and concurrent-writer behaviour undefined | E, A | New decision [0015](../../decisions/0015-ledger-integrity-and-record-trust.md): single writer, framing, key recomputed on read, origin and signature for shared records, causal order instead of a counter |
| "No ambient authority" was claimed and cannot be delivered equally on every platform | E | New decision [0016](../../decisions/0016-provider-isolation-is-stated-not-assumed.md): isolation level recorded per run, policy can require one |
| Build outputs were not in the evidence key, so a compiler change would not invalidate tests of its output | A | Artifacts are nodes produced by build obligations; consumers depend on the producer's inputs |
| The platform in the key was the kernel's, not the one the check ran on; remote executors never reported what they ran | A, C, E | Key split into core key and executing platform; executor reports platform and tool digests; mismatch is `error` |
| Platform inside one opaque hash made cross-platform comparison impossible, and a platform-independence claim would suppress the very check it relies on | A, C | Records are paired by core key; one platform alone gives reproducibility `unknown`; the claim never removes the platform |
| Executor was synchronous; `pending` had no source; long remote runs would be lost or duplicated | A | `run.submit`, `run.poll`, `run.cancel` with a handle |
| One run per check could not express compile-then-test or trace replay | A | Next-run-or-final loop, every run recorded |
| Content-addressed identity alone cannot tell an edit from a deletion | A | Definitions have a stable name and a content identity; decisions govern names |
| Tool digest undefined for anything but one file; runtimes such as a JVM were unpinned | C, E | Tools are trees with a canonical listing digest and a pinned requirement closure |
| Path, line-ending, byte-order-mark and symlink rules were incomplete and untestable from a schema | C | One normative path check with published vectors; declared line-ending rule; links rejected; vectors stored as data |
| Message framing, argument passing and process termination were underspecified for Windows | C | Exact framing, exact program files inside tool trees, no interpreter wrappers, whole process tree terminated, bounded output |
| Canonical encoding and sort order undefined | C | UTF-8 byte order, integers only; vectors still to be written |
| Fixed evidence-class list contradicted the conformance methods and would need a kernel change per new kind of tool | A, D | Provider-named class with a kernel-owned strength rank |
| A pass needed no evidence; proofs resting on unproven assumptions had no defined verdict | E, D | Every record carries exit status and raw output digest; per-record trusted base; an unpermitted assumption is `failed` |
| No bounds on a hanging or flooding provider; late results undefined | E | Deadlines, size caps, late answers dropped |
| The bootstrap did not state where trust comes from; self-checking stages were implied to add trust | B, E | Stages now say what each establishes; first seed trusted by review; independence requirements; disagreement is `conflict` |
| The model's main property was near-trivial, never showed reuse happening, and one property had no planted defect | B | Model extended: flaky provider, provenance history, conflict, reuse reachability, a defect for every property; claims reworded with bounds and assumptions |
| Claims table had unfilled placeholders and shared statuses | B, D | Each modelled claim has its own status, and a place for its recorded run |
| Trusted-base lists disagreed between documents | B, E | One list, in the data model |
| Configuration could bind only whole providers | A | Bindings are per capability with file claims |
| Terms used with two meanings | D | Defined once in the data model |

## Accepted, not yet acted on

Specific findings that are right and have no change behind them yet:

- A published table of test cases for passing argument lists on Windows without a shell, and a cap on total argument size with an arguments-file mechanism. (C)
- For tools declared nondeterministic: how many agreeing runs are needed before a status is given. (C)
- A periodic check on a second platform even for providers whose platform-independence claim was verified. (C)
- A configuration reference: every table, key and the version-constraint grammar. (D)
- A model with two kernels writing one ledger, and with crash points. (B, E)
- A model in which dependency sets change, and one with a state space that needs no bound on runs in flight. (B)
- A way to retire named records after a conflict, and what it records. (B)
- Cross-building between two kernels: each builds the other's source and the results are compared. (B, E)
- A kernel-checked completion marker that a verifier names in advance, so truncated tool output cannot be read as a pass. (E)
- Handling of side effects when an executor loses a run after the tool has written something. (E)
- The model checker and the runtime under it are in dodona's own trusted base and are not yet pinned by digest. (B, E)

## Open design questions after draft 0.2

- How policy is protected from the agent it constrains.
- The signing scheme for shared records.
- Message schemas per capability, the run description, the lock, policy, and the agent interface as schemas. Until they exist, a third party cannot write a provider from this repository.
- The canonical encoding and the path check as vectors.
- Most claims are not yet modelled; see [the claims table](../../spec/CLAIMS.md).
- Independence between two kernels written by similar agents from one specification remains a residual risk.
- Tools that exist only as installers.
